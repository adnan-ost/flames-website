Deploying to the cPanel box

Bare server to live site. Follow the phases in order, because several steps only work once an earlier one is in place. Every step ends with a command that proves it worked before you move on.

GitHub (main) └─ push → Actions → ssh → /srv/flames/repo/deploy/release.sh <sha> │ ├─ build into releases/<sha>/ ├─ swap current → releases/<sha> (only if build passed) └─ sudo systemctl restart flames Apache/nginx :443 ── proxy ──> Next.js 127.0.0.1:3000 (systemd unit `flames`) Sanity (byr90f6b/production) ── menu, images, prices
PHASE 0

Decide before you touch anything

One decision governs the whole deployment, and getting it wrong means undoing work. Make it now.

Who owns port 443?

On a WHM/cPanel box, Apache already owns 80 and 443. The nginx.conf.example in the repo assumes nginx owns them. Both cannot be true, so pick a lane.

Recommended

A · Apache reverse proxy

Keep cPanel's Apache in front, proxy to :3000. Native to cPanel, AutoSSL keeps working, other accounts on the box are unaffected.

B · ea-nginx in front

Install cPanel's own nginx package. Config goes in EA4's structure, not /etc/nginx/conf.d, so the repo file needs adapting.

C · Plain nginx, Apache off

Only if this box hosts nothing but this site. Uses the repo config as written, but breaks every cPanel-managed vhost.

If this server hosts other cPanel accounts, C is not an option.

Stopping Apache takes every other site on the box down with it. Choose A unless you are certain this machine serves only Flames.

0.1

Point SITE.url at the real domain, and push

NEXT_PUBLIC_* values and canonical URLs are baked in at build time. If this is wrong when the server builds, every page advertises a canonical URL that is wrong, which is worse for SEO than having none. Fix it before the first build, not after.

# on your laptop
grep -n "url:" src/lib/site.ts   # must read https://flamesbytheindus.com
0.2

Check the Node version the flames user will get

Next 16 needs 20.9 or newer. cPanel boxes often carry several Node installs, and the one root sees is frequently not the one a service user sees. release.sh refuses to build below 20 rather than failing halfway, so check now.

node -v
sudo -u flames node -v   # this is the one that matters
PHASE 1

Prepare the server

Run as root. Creates the app user, the directory layout, and the clone the deploy script fetches from.

1.1

User and directories

adduser --system --group --home /srv/flames flames

mkdir -p /srv/flames/{releases,shared}
git clone https://github.com/adnan-ost/flames-website.git /srv/flames/repo
chown -R flames:flames /srv/flames
Verify

ls -la /srv/flames shows repo, releases, shared, all owned by flames.

1.2

Build-time environment

Two variables only. The Sanity write token does not go here. The site never reads it, and it can destroy all your content.

cat > /srv/flames/shared/.env.local <<'ENV'
NEXT_PUBLIC_SANITY_PROJECT_ID=byr90f6b
NEXT_PUBLIC_SANITY_DATASET=production
ENV

chown flames:flames /srv/flames/shared/.env.local
chmod 600 /srv/flames/shared/.env.local
Ignore .env.example here

It lists SANITY_API_WRITE_TOKEN because laptop scripts need it. Copying that file onto the server puts an Editor-scoped token on a public web host for no benefit.

PHASE 2

Install the service

2.1

systemd unit, bound to localhost

Add the HOSTNAME line. Next binds 0.0.0.0 by default, which would leave port 3000 reachable from the internet and let anyone bypass TLS entirely. Pinning it to loopback means the only way in is through the proxy.

cp /srv/flames/repo/deploy/flames.service /etc/systemd/system/

# add this under [Service]:
Environment=HOSTNAME=127.0.0.1

systemctl daemon-reload && systemctl enable flames
Verify after the first release

ss -lntp | grep 3000 must show 127.0.0.1:3000, never 0.0.0.0:3000 or *:3000.

2.2

Let the deploy user restart the service

One command, no password. Scoped deliberately: not ALL.

echo 'flames ALL=(root) NOPASSWD: /bin/systemctl restart flames' > /etc/sudoers.d/flames
chmod 440 /etc/sudoers.d/flames
Verify

sudo -u flames sudo -n systemctl restart flames runs without prompting. If it says command not allowed, check whether systemctl lives at /usr/bin/systemctl on this box and correct the path.

PHASE 3

First release, by hand

Prove the build pipeline works before wiring CI to it. Debugging a broken build through GitHub Actions logs is far slower than doing it at the shell.

3.1

Run the release script

sudo -u flames APP_DIR=/srv/flames \
  /srv/flames/repo/deploy/release.sh \
  "$(git -C /srv/flames/repo rev-parse origin/main)"

It fetches, builds into releases/<sha>/, and only moves the current symlink if the build succeeded. Expect a few minutes for npm ci and the build.

Verify

It prints ==> live on <sha>. Then curl -s localhost:3000/menu | head returns HTML containing dish names.

If the build dies on memory

124 dishes with image optimization is the heaviest step. Give it swap, or set NODE_OPTIONS=--max-old-space-size=2048 in shared/.env.local and re-run.

PHASE 4

Put a web server in front

Steps below assume Option A, Apache reverse proxy, the cPanel-native path. For B or C, use deploy/nginx.conf.example instead and skip to 4.3.

4.1

Proxy the domain to :3000

In WHM → Apache Configuration → Include Editor → Pre VirtualHost Include, or as a userdata include for the domain. Do not hand-edit httpd.conf: cPanel regenerates it and your change disappears.

ProxyPreserveHost On
ProxyPass        / http://127.0.0.1:3000/
ProxyPassReverse / http://127.0.0.1:3000/
RequestHeader set X-Forwarded-Proto "https"
Turn buffering off

Buffered responses defeat streaming and Suspense. On Apache add SetEnv proxy-sendchunked 1 and avoid mod_deflate on proxied HTML.

4.2

Certificate

Use cPanel's AutoSSL (WHM → Manage AutoSSL → run for the domain). Do not run certbot --nginx on a box where Apache terminates TLS, since it configures the wrong server.

Verify

curl -sI https://flamesbytheindus.com | head -1 returns 200 with no certificate warning.

4.3

Security headers, and HSTS last

Only enable HSTS once the certificate is confirmed working. It pins browsers to HTTPS for six months. Shipped before TLS is right, it locks visitors out for that entire period, and you cannot recall it.

Header always set X-Content-Type-Options "nosniff"
Header always set Referrer-Policy "strict-origin-when-cross-origin"
Header always set Content-Security-Policy "frame-ancestors 'self'"

# only after 4.2 verified clean:
Header always set Strict-Transport-Security "max-age=15768000"

frame-ancestors 'self' rather than 'none', because Sanity's Presentation mode iframes the site from /studio on the same origin.

4.4

Close port 3000 at the firewall

Belt and braces alongside the HOSTNAME binding in 2.1. cPanel boxes usually run csf.

csf -g 3000   # should show no public allow rule
Verify from your laptop, not the server

curl -m 5 http://<server-ip>:3000 must time out or refuse. If it returns the site, the app is exposed without TLS.

PHASE 5

Reconnect Sanity

5.1

Register the new origin

Sanity CORS is per-origin, and only localhost:3000 is currently allowed. Visit https://flamesbytheindus.com/studio and click Register Studio on the prompt that appears.

Use Register Studio rather than Add CORS origin: it also registers the schema, which is what powers schema-aware search and Content Agent.

Verify

The Studio loads your 20 categories and 124 dishes instead of Connect this Studio to your project.

PHASE 6

Hand the keys to CI

Only once a manual release has succeeded end to end.

6.1

A deploy key, for this purpose only

Generate fresh. Never reuse a personal key, since anyone with repo admin can read what you paste into a secret.

ssh-keygen -t ed25519 -N '' -C 'github-deploy' -f ./flames-deploy

sudo -u flames mkdir -p /srv/flames/.ssh
sudo -u flames tee -a /srv/flames/.ssh/authorized_keys < ./flames-deploy.pub
chmod 700 /srv/flames/.ssh && chmod 600 /srv/flames/.ssh/authorized_keys
6.2

Repository secrets

Settings → Secrets and variables → Actions.

SecretValue
DEPLOY_HOSTserver hostname or IP
DEPLOY_USERflames
DEPLOY_SSH_KEYcontents of ./flames-deploy, then delete your local copy
DEPLOY_KNOWN_HOSTSoutput of ssh-keyscan -H <host>

DEPLOY_KNOWN_HOSTS is not optional. Without it the deploy trusts whatever host answers, so a hijacked DNS record could capture the SSH session.

6.3

Switch the workflow on

The job is gated off so it cannot fail on every push before the server exists. Settings → Secrets and variables → Actions → Variables:

DEPLOY_ENABLED = true
Verify

Actions → Deploy → Run workflow. It must reach Confirm the public site is answering and print live (200).

PHASE 7

Prove it end to end

7.1

The checks that catch real breakage

curl -sI https://flamesbytheindus.com | head -1        # 200
curl -s https://flamesbytheindus.com/menu | grep -c Karahi
curl -s https://flamesbytheindus.com/robots.txt        # disallows /studio
readlink /srv/flames/current                           # matches the SHA in Actions

Then look at the site in a browser, hard-reloaded. Confirm hero images load: those come from Sanity's CDN, and the local masters under public/menu-items are gitignored, so they do not exist on the server at all.

This exact thing caused a live outage before

Every hero image 400'd in production while working perfectly on localhost, because one code path built its own /menu-items/... URL instead of going through dishImageUrl(). If an asset is gitignored, nothing may depend on it at runtime.

7.2

Know the rollback before you need it

Five releases are kept, so recovery is a symlink swap and a restart. Roughly ten seconds.

ls -1dt /srv/flames/releases/*/          # newest first
ln -sfn /srv/flames/releases/<previous-sha> /srv/flames/current
sudo systemctl restart flames
REFERENCE

Traps already paid for

Each of these has cost real debugging time on this project. Check them before assuming a bug is in the code.

Site serving old content

A silently failed deploy leaves the previous release up. Compare readlink /srv/flames/current against the SHA in Actions before looking anywhere else.

Env change had no effect

NEXT_PUBLIC_* are inlined into the JS bundle at build time. Editing shared/.env.local and restarting does nothing. It needs a rebuild.

Sanity edits never appear

ISR writes under .next/cache. If the release directory is not writable the site still serves but freezes at build-time content. ReadWritePaths=/srv/flames in the unit covers it.

Hydration mismatch after deploying

Caused by running next build while next dev is live on the same checkout. They share .next. Not a component bug.

Headers missing on some routes

Any location or <Directory> block that sets its own header silently drops every inherited one. The security headers must be repeated wherever Cache-Control is set for /_next/static/.

Old QR codes stop working

menu.flamesbytheindus.com is being removed with no redirect, by decision. Anything printed pointing at it will stop resolving. Reprint against the apex.

Content operations stay on your laptop. npm run sanity:seed and npm run sanity:prices need SANITY_API_WRITE_TOKEN, which deliberately never reaches the server.
